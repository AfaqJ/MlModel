**Historical payload — this was pushed to production on 2026-08-19 and live has
moved past it since** (the canonical catalog migration, D-044/D-045, reduced
`item_catalog` to 4,029 rows). It is kept as the record of what v1.3.3 shipped,
not as something to re-run. The script that produced it and the uploaders that
consumed it were deleted on 2026-08-26.

## One DDL change is required first

`001_extend_prediction_source_check.sql`. The declared CHECK allows only
`model`, `product_lookup`, `meter_lookup`, but 1,301 rows carry finer
provenance: `business_rule`, `client_evidence_backfill`, `silver_audit_backfill`,
`manually_audited_near_identical_backfill`.

That distinction is worth keeping — it is what answers "was this row proven by
the client or decided by the model?" after the fact, and it is how the 874
model/silver rows stay auditable. Run the ALTER before importing.

If you would rather not change the constraint, re-run with
`--collapse-prediction-source`, which folds the four extra values into the
allowed three and loses that traceability.

## Review-state contract

Follows the schema's own design; `needs_review` is a generated column and is
never written.

| column | on import | after a reviewer acts |
| --- | --- | --- |
| `decision` | `auto_accept` (6,583) or `review_required` (5,183) | unchanged |
| `reviewed` | **false on all 11,766** | set true |
| `needs_review` | computes to true for the 5,183 | computes to false |
| `final_code` / `final_categories_id` | filled on the 6,583 auto-accepts, NULL on review rows | reviewer sets it |

So the table always separates what the model decided from what a person
confirmed.

## Columns intentionally not written

Generated by Postgres: `invoices.invoice_period`, `invoice_items.needs_review`,
and all `*_id` primary keys.

Dropped from the bundle, with nothing lost:
- `xml_document_kind` — `document_type = '43'` already identifies the 29
  Liquidación invoices.
- `source_file` — no column; recoverable from
  `(seller_rut, document_type, invoice_folio)`.

## Natural keys

Fields prefixed `_` are for foreign-key resolution and **must be stripped before
insert**:

- `invoices._company_rut` → `companies.company_id`
- `invoice_items._seller_rut`, `_document_type`, `_invoice_folio` → `invoices.invoice_id`
- `invoice_items._catalog_item_name`, `_catalog_description` → `item_catalog.catalog_item_id`
`predicted_categories_id`, `final_categories_id` and the `categories_id` inside
each `top3` element are **already resolved** against this database's `categories`
table, so no lookup is needed for them. That makes this payload specific to
project `nkdswofslslrumyraklv`; regenerate it if the target changes.

## How to run it

There is **no cross-table transaction** — PostgREST cannot give one. Three things
compensate: stages are ordered so dependencies land before dependants (a failure
leaves a valid, partially-updated database, never a broken one); every stage
verifies its own count and aborts rather than continuing; and every write is an
idempotent upsert or a delete of an already-identified row, so a failed run can
simply be re-run. **Your backup is the real rollback.**

The upload commands that used to sit here have been removed: they drove
`scripts/79`/`scripts/80`, both deleted on 2026-08-26, and re-running them
against today's database would fight the canonical catalog migration. This
section is left as a description of what was done, not a procedure to repeat.

`--execute` alone is refused; both flags are required.

### Stages

| # | action | conflict key |
| --- | --- | --- |
| 1 | upsert `categories` | `code` |
| 2 | upsert `companies` (+1) | `rut` |
| 3 | upsert `item_catalog` (+48) | `item_name,description` |
| 4 | resolve `_company_rut`; upsert `invoices` (+38) | `seller_rut,document_type,invoice_folio` |
| 5 | resolve invoice + catalog ids; upsert `invoice_items` (11,654 updated, +112) | `invoice_id,invoice_line_number` |
| 6 | delete the junk item rows — **417 land, not 440**; the other 23 name line numbers the old parser never created | `invoice_id` + `invoice_line_number` |
| 7 | re-check the 225 orphan catalog rows are unreferenced, then delete them | `catalog_item_id` |
| 8 | verify | — |

Stage 7 re-queries live rather than trusting the pre-flight: it is the only
destructive step whose safety depends on stage 6 having actually completed. If
anything still references those rows it aborts and deletes nothing.

Progress is appended to `reports/recovery_v1_3_3/upload_log.jsonl`.

## Deliberate divergences from the live rows

Not corruption — check these off during verification rather than investigating them:

- **`product_lookup` scoring.** Live product_lookup rows carry `margin != 1.0`,
  `entropy != 0` and three `top3` entries. In this payload those 2,640 rows (and
  the 137 `business_rule` rows) use the collapsed deterministic form —
  `top1_score = 1.0`, `margin = 1.0`, `entropy = 0`, one `top3` entry — matching
  how live already represents `meter_lookup`. A lookup hit is not a probability.
- **Backfill rows** (`client_evidence_backfill`, `silver_audit_backfill`,
  `manually_audited_near_identical_backfill`) use the same collapsed form, for
  the same reason.
- **`model_version`** moves from `v1.1.0` to `v1.3.3` on every row. That is the
  release stamp; the weights are `models/setfit_base_recovery_v1_3_2`, and the
  pairing is recorded in `manifest.json` under `model_binary`.
