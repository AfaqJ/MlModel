# Focused recovery v1.2.0

Status: local candidate work only. Nothing in this recovery has been pushed,
deployed, uploaded, or written to Supabase.

## Scope

This recovery starts from the last gold snapshot before Claude's broad data
promotion and fixes the original milk-sales incident without accepting unrelated
labels. The source files and v1.1 model remain unchanged.

The candidate is generated by `scripts/59_build_focused_recovery_gold.py`:

- start: 1,733 pre-Claude gold rows;
- quarantine: 3 COMPRAS rows incorrectly labeled as income (`SA-00757`,
  `SA-00758`, `SA-00874`);
- add: 105 distinct raw VENTAS rows whose exact item phrase names a verified
  sales category;
- final: 1,835 provenance rows, 1,580 distinct model inputs after the same text
  cleaning used in training;
- synthetic rows: 0;
- cross-label model-input contradictions: 0.

Income coverage is `ING-0.1=47`, `ING-0.2=15`, `ING-0.3=2`, and `ING-0.4=46`.
There is no real verified example for `ING-0.5` or `ING-0.6`, so neither is
invented. `ADM-1.9` has only one example and is excluded loudly rather than
silently disappearing.

All generated CSVs and their input hashes are recorded in
`Data/candidates/recovery_v1_2_0/manifest.json`. The locked split is
`split_seed42.csv`: 1,268 training inputs, 311 validation inputs, one excluded
input, and zero normalized train/validation overlap.

## Exact transaction lookup

Five phrases observed in raw VENTAS are authoritative exact matches:

- `VENTA DE LECHE` -> `ING-0.1`
- `VENTA DE VACAS` -> `ING-0.2`
- `VENTA DE VAQUILLAS` -> `ING-0.3`
- `VENTAS TERNEROS` -> `ING-0.4`
- `VENTA DE TERNERAS` -> `ING-0.4`

They are keyed by both normalized item text and `transaction_type=VENTAS` and
short-circuit the model. The same text under COMPRAS does not match. Unverified
firewood and asset-disposal rules from the previous attempt were removed.
Unknown VENTAS items may receive a model suggestion for review, but can never be
auto-accepted. All `ING-*` classes are removed from COMPRAS rankings.

## Full SetFit training and the MPS memory fix

Frozen token embeddings are rejected for the release candidate. The recovery
trainer asserts that all 278,043,648 encoder parameters are trainable and fails
if the token embedding table is frozen or does not change.

The previous diagnosis blamed the 732 MiB embedding gradient and AdamW. The
controlled runs show that diagnosis was incomplete:

| Run | Padding | Optimizer / batch | MPS driver memory |
|---|---|---|---|
| initial smoke | dynamic | Adafactor / 4 | 5.05 -> 14.41 GiB in 12 steps |
| repaired smoke | fixed 64 | Adafactor / 4 | 4.42 GiB plateau through step 20 |
| release configuration | fixed 64 | AdamW / 8 | 6.60 GiB plateau through step 20 |

Live tensors stayed flat in the failing run while driver memory grew by about
one embedding-sized allocation per new batch shape. Padding every contrastive
batch to the already-selected 64-token maximum makes MPS reuse one graph shape.
That stops the growth and permits standard AdamW, batch 8, full encoder updates,
and the normal bounded MPS watermark. No `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0`
is allowed by the recovery trainer.

The final candidate uses the v1.1-comparable budget of 1,500 SetFit embedding
steps and completed in 22.46 minutes. MPS driver memory peaked at 6.61 GiB and
did not grow across the run. The tracked token-embedding change was
`0.0023982`, confirming that the table was updated rather than frozen.

On the 311-row locked candidate validation split:

- accuracy: `0.7524`
- macro-F1: `0.7316`
- top-3 accuracy: `0.8746`
- canonical income slice: `21/21` top-1 and top-3

The income result is not claimed as generalization to unseen wording: the held
out invoice rows have distinct full model inputs, but intentionally share their
verified canonical item phrase with training. The exact transaction lookup—not
the metric—is the production safety guarantee for those five phrases.

An initial baseline comparison on the candidate split was rejected as
confounded because many of those rows were part of v1.1 training. That failed
diagnostic is retained as `reports/recovery_v1_2_0/model_comparison.json`.

The formal shared-blind comparison starts from v1.1's own validation rows, then
removes any input duplicated in original gold and anything present in candidate
training. This leaves 58 non-income rows unseen by both models:

| Metric | v1.1 | recovery | delta |
|---|---:|---:|---:|
| Accuracy | 0.6034 | 0.7069 | +0.1035 |
| Macro-F1 | 0.5886 | 0.6323 | +0.0437 |
| Top-3 accuracy | 0.8103 | 0.8621 | +0.0518 |

The shared set is small and contains no income rows, so it is a regression gate,
not a comprehensive performance claim. The larger candidate split measures the
new model honestly; the exact rules separately guarantee the known sales cases.

`scripts/62_validate_recovery_release.py` passes every local release check, and
the full local test suite passes `15/15`. Reports are under
`reports/recovery_v1_2_0/`.

## Known limitations kept explicit

- `ADM-1.9` has one real input and is excluded from the model.
- `ING-0.5` and `ING-0.6` have no verified real sales examples in this corpus.
- `ING-0.3` has two distinct inputs and is train-only/weak; its verified exact
  phrase is protected by the lookup.
- Seven VENTAS rows are asset/other-income phrases with no verified category;
  they are forced to review rather than auto-accepted.
- No ONNX export was attempted. The inherited exporter can select the wrong
  tagged model and deletes an existing artifact directory before its parity
  gate. The validated local deliverable is the PyTorch SetFit candidate until a
  fail-closed exporter replaces it.
- Nothing is deployed. Local API contract tests do not imply a remote service
  exists.
